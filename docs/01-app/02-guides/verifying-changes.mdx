---
title: How to verify a change in a running Next.js app
nav_title: Verifying changes
description: Check a page for render errors, test what users see during an interaction, and decide when you need a production build.
---

Start with the behavior you changed. Next.js can tell you whether a route compiles and whether its server render reports an error. To find out whether a button responds, content moves, or the right data appears after a click, exercise that interaction in a browser.

## Check the route while editing

Suppose you've changed the product page at `/products/mug`. Start `next dev`, or use the server already running for the project. With [Next.js DevTools MCP](/docs/app/guides/mcp) connected, use `nextjs_index` to discover the server and its tools. If it lists `check_route`, use `nextjs_call` to call it with `{"path":"/products/mug"}`. Use a concrete URL from the app, including the query string if it changes what's rendered.

You can also call the running dev server directly. Use the port printed by `next dev`:

```bash filename="Terminal"
curl -sS http://localhost:3000/_next/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

If the list includes `check_route`, send a second request to the same endpoint with this body:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": { "name": "check_route", "arguments": { "path": "/products/mug" } }
}
```

Read the tool result, including `httpStatus`, `compilationIssues`, and `validation`. With Cache Components enabled, `validation.status: "validated"` and an empty `errors` array mean the render passed that validation. An error can include an app source location. If the status is `"not-run"`, read the reason: for example, a redirect means the requested page did not render. A successful HTTP response or `ok: true` alone doesn't establish that validation ran. For a page that needs a signed-in session, also open it in that session.

## Try the interaction before and after the data arrives

Open the product list and **click its link** to the product. Typing the product URL tests a direct visit; it skips the list, the link's prefetch, and the user's click. Use a fresh browser context for the first visit, then navigate away and back to see what changes on a repeat visit.

Give the slow response time to remain pending. If you're checking a [prefetched navigation](/docs/app/guides/optimizing-prefetching), use the [Playwright `instant()` helper](/docs/app/guides/testing/playwright#testing-instant-navigations). Assert what should already be visible **inside** the hold, then release it and check the final content. An assertion made only after the response arrives can't tell you what the user saw while waiting.

For example, if the product name should appear immediately but availability loads later, check that the name and navigation remain usable, that the stock area shows feedback, and that the purchase button doesn't move under the pointer when the stock arrives. Repeat at a narrow viewport. For a filter or selection, try a second choice while the first is pending; confirm which choice is active and which result eventually wins. Check the browser console and the development overlay after the interaction, including hydration errors that a server request cannot see.

Use your browser, an existing browser test, or the [Dev Loop skill](/docs/app/guides/ai-agents#next-dev-loop) for this step. A screenshot of the settled page won't show an earlier layout shift. If a performance recording has no sample for the interaction, repeat the measurement before drawing a conclusion.

## Reproduce production behavior when it matters

Use a normal `next build` and `next start` for a final check of production output or automatic link prefetching. Repeat the same click from the same starting page. When you change a cache, test the underlying data too: update the product through the app, reopen it, and verify that the new value appears. If the page also has private data, check a second session to make sure it sees its own values.

If a prerender error appears only during the build, run [`next build --debug-prerender`](/docs/app/guides/building#debug-prerender-errors) to get readable server frames. For a large app, [`--debug-build-paths`](/docs/app/api-reference/cli/next#building-specific-routes) can narrow the investigation to the affected routes. Use a normal build for the final verification; don't deploy the diagnostic build.
