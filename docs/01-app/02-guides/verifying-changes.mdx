---
title: How to verify App Router changes with a coding agent
nav_title: Verifying changes
description: Use the running Next.js server to check a route, then test what the user sees before and after an interaction.
---

Suppose you've changed a product page. Does it render without errors? Does the purchase button move when stock arrives? The dev server can answer the first question. For the second, open the app and try the click.

## 1. Check the changed route

1. Start `next dev`, or reuse the server already running for the project.
2. With [Next.js DevTools MCP](/docs/app/guides/mcp), use `nextjs_index` to list the server's tools. If it lists `check_route`, use `nextjs_call` to call it with a real path, such as `{"path":"/products/mug"}`. Include the query string if it affects the page.
3. Read `compilationIssues` and `validation`. With Cache Components enabled, `"validated"` with no errors means this render passed. If you get an error, follow its source location and check the route again. If you get `"not-run"`, read the reason: a redirect, for example, means the requested page never rendered. Even `ok: true` can accompany a skipped validation.

<details>
<summary>Call the dev server directly without an MCP client</summary>

Use the port printed by `next dev`:

```bash filename="Terminal"
mcp() {
  curl -sS http://localhost:3000/_next/mcp \
    -H 'Content-Type: application/json' \
    -H 'Accept: application/json, text/event-stream' \
    -d "$1"
}

mcp '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

If the server lists `check_route`, call it with the path you changed:

```bash filename="Terminal"
mcp '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"check_route","arguments":{"path":"/products/mug"}}}'
```

</details>

## 2. Try the click in a browser

Start from the product list in a fresh browser session and click the product link. Opening its URL directly skips [link prefetching](/docs/app/guides/optimizing-prefetching). Use the browser you already have, a Playwright test, or the [Dev Loop skill](/docs/app/guides/ai-agents#next-dev-loop).

| When                   | What to check                                                                                                                                                                                                                                   |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| While stock is loading | The product name is visible, the stock area shows feedback, and the navigation still works. With Playwright's [`instant()` helper](/docs/app/guides/testing/playwright#testing-instant-navigations), make these assertions **inside** the hold. |
| When stock arrives     | The placeholder gives way to the stock count without moving the purchase button. Try a narrow viewport and check the console and dev overlay for errors.                                                                                        |
| On a repeat visit      | Change the product or selection, navigate away, then come back. Verify the current value. For private data, repeat in a second session and check that each user sees their own data.                                                            |

## 3. Check production behavior when it matters

- **Checking automatic prefetching or production output?** Run a normal `next build` and `next start`, then repeat the same navigation.
- **A prerender error only appears during the build?** Use [`next build --debug-prerender`](/docs/app/guides/building#debug-prerender-errors) for readable server frames. In a large app, [`--debug-build-paths`](/docs/app/api-reference/cli/next#building-specific-routes) limits the build to selected routes. Don't deploy the diagnostic build.
